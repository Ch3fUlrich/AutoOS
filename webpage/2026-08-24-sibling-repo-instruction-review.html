C3New Rule 11

HDF5 concurrency discipline is absent — the repo's most expensive failure class

4 must rules in the graph · MasterHDF5Store is graphify's #1 god node at 431 edges (next is 267)

Rule 6 covers symmetric storage and nothing covers locking. The concrete cost on record: one held read-only handle starved 49 healthy video items in four minutes, because a read-only holder still takes the OS lock.

Rule 11 covers
  • serialise on hdf5_lock.hdf5_write_lock(path);
  • batch results enter via staging + auto_merge, never by writing master directly;
  • never set HDF5_USE_FILE_LOCKING;
  • read via read_snapshot(path, reader) (hdf5_open.py:336) — a read-only holder still takes the lock.
C5Amend Rule 3

Rule 3 is itself the vector for a known data-loss bug

AGENTS.md:135 · ba-rule-reread-shared-files-before-prepending (must)

Rule 3 mandates writing into changelog.md and says nothing about re-reading first. On 2026-08-24 between 12:05Z and 12:14Z changelog.md silently lost a 71-line section when a concurrent session wrote from a stale in-memory copy — recovered only from a sibling worktree's index. A MANDATORY rule that reliably produces the write pattern which destroys data is worse than no rule.

Amend in place
  • re-read immediately before writing;
  • edit in binary — Windows write_text rewrites whole LF files to CRLF and buries the hunk;
  • multi-agent waves get worktree isolation (ba-rule-isolate-multi-agent-waves-in-a-worktree).
