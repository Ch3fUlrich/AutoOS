What the Starter Ships

A configuration audit of sibling-analysis-repo found six gaps. Five of them were inherited, and this repository is where they were inherited from. Fix the source and every repo set up after today starts closed — six findings, measured here.

2026-08-28 main @ b8690e7 13 skills · 5 ADRs · 22 Rule nodes
The verdict

The downstream findings are symptoms. The mechanism that copies them lives in starters/.

The sibling-analysis-repo audit is right, and its central observation transfers upward without modification:

Until that import existed, the rules reached an agent only if it chose to obey a prose instruction to go and read another file. That is a hope, not a mechanism. sibling-analysis-repo · tests/test_instruction_files_are_loadable.py

That repo has one copy of the problem. This repo is the press. starters/mcp-servers/ is what a new repository is set up from, and it currently ships prose that points at files which do not exist in the target, names tools that do not exist at all, and carries one specific project's domain rules into every repo that copies it. It ships no .mcp.json, no .claude/settings.json, and no wiring that would put a single skill on a load path.

So the good news is leverage: five of six fixes are one edit, in one directory, and they close the gap for every future setup rather than one repo at a time.

Finding 1

The skills library works on exactly one machine, by a mechanism nothing records

F113 skills, 3 doors, 0 tracked

not loaded

Claude Code discovers skills from three places: .claude/skills/, ~/.claude/skills/, and installed plugins. This repo tracks none of the first two and carries no .claude-plugin/ marker, so nothing in git puts repository-index — the file AGENTS.md opens by saying "Read it first" — anywhere an agent will find it without being told to go looking.

Measured on this workstation today, the skills do load — all 13 appear in the session listing — because ~/.claude/skills/ holds 13 symlinks pointing back into skills/, created by hand at 12:11 this morning. That is a real fix and it works. The problem is that it exists nowhere else: AGENTS.md, CLAUDE.md, CONTRIBUTING.md, mcp-servers-setup/SKILL.md and the starter README all say nothing about it.

A fresh clone, a second machine, CI, or a cloud session therefore gets zero skills — and gets no error either. The agent just works worse, which is the failure mode this repository writes about more than any other.

Declared ≠ live. Verify against the running system, never against a config file or a script's own report. CONTRIBUTING.md — "The rule behind most of the others"

The fix is a tracked .claude-plugin/plugin.json plus a local marketplace.json, so the library installs as a versioned plugin on any machine, with an idempotent link script kept as the dev-loop path (a symlink gives live edits; an install gives a copy). Whichever you pick, the verification is the same and it is the part that matters: the skill names must appear in the session listing, not merely on disk.

The starter is a copy of four skills, and it points at paths that only resolve here

propagates

This repository states the rule twice — once in AGENTS.md ("instruction files and starters are pointers"), once in CONTRIBUTING.md ("thin per-repo adapters that POINT at a skill, never copy it") — and once more as the skill-single-source Rule node in the graph. The starter does the opposite.

The last row is worth dwelling on. That paragraph is sibling-analysis-repo's own Rule 1 — the audit's rule table lists it as "R1 batch processing · scripts/**". It reached the generic starter, and from there it reaches everything. Nobody set out to do that; it is what a starter that is a copy does automatically.

The structural fix is that a starter must be checkable from outside: copy it to a scratch directory and resolve every path and tool name from there. Inside agent-skills the paths happen to work, which is exactly why reading the file here never catches it.

Findings 3 & 4

Nothing is committed, and nothing is checked

F3The one line a fresh clone needs is in the gitignored file

local only

.claude/settings.local.json in this repo contains exactly this: 

{ "enabledMcpjsonServers": ["omnigraph"] }

Nothing in it is secret. But it is gitignored — correctly, since that is where OMNIGRAPH_TOKEN belongs — so a fresh clone of this repository starts with the memory graph switched off and no message saying so. The tracked .mcp.json cannot approve itself; that is documented in CLAUDE.md's own failure table, as the row whose symptom is "MCP tool absent entirely — no prompt, no error".

Split it: non-secret enablement, permissions and hooks into a tracked .claude/settings.json; the token stays behind. The starter should ship the same pair, plus the .mcp.json template it currently describes in prose but does not provide.

F4The repo that authored the convention has no test for it

unenforced

sibling-analysis-repo has tests/test_instruction_files_are_loadable.py. This repository — which owns the rules that test defends — has no tests/ directory at root at all. Every test here sits under infra/ or inside swarm-orchestration/, and none of them looks at an instruction file, a skill, or a starter.

The cost is not hypothetical. The graph carries a Rule that says "No personal absolute paths or secrets in tracked files". Nine tracked files violate it today:

Four invariants are cheap to test and would each have caught something real: every skill resolves by name at runtime; every skill has a row in the router (true today — nothing keeps it true); no tracked file contains a personal absolute path; every path and tool name in a starter resolves from outside this repo. Hooks are the heavier half of the same idea and can follow ADR 0004; the tests do not need to wait for it.

The tables state when and instead of what; they restate no tool list, so each SKILL.md stays the single home. The escape hatch is deliberately non-silent: fall back if a server is genuinely down, but name which one and why. An unreported fallback is what makes a config bug — an unset token, a user-scope shadow — indistinguishable from a fact about the repository. That is how the 2026-07-17 "the graph was wiped" incident started.

Build order

Five steps, sequenced by dependency

Step 1 puts the skills somewhere the harness looks, which is what lets steps 2 and 3 move material out of the starter without losing it. Steps 4 and 5 are independent and can happen any time.

  1. Put the skills library on a tracked load path

    ~45 mintrackedunblocks 2 & 3

    Add .claude-plugin/plugin.json and a local marketplace.json, so the library installs by name on any machine and carries a version. Keep an idempotent scripts/link-skills.{ps1,sh} as the development path — symlinks give live edits, an install gives a copy, and both are useful for different reasons.

    Document it in CONTRIBUTING.md and in the starter README, then record it as a Decision in the graph, because the current mechanism exists only in one machine's filesystem.

    Verify by name, not by path. The skills must appear in the session's skill listing after a restart. Files on disk are not evidence — that is the same class of claim as reading a config to prove a server is live.

  2. Rewrite the starter as a pointer, and check it from outside

    ~1.5 hrhighest leverageevery future repo
    • Delete the copied Serena table, Omnigraph protocol and Superpowers list. Replace each with one line naming the skill and the trigger.
    • Replace skills/<name>/SKILL.md relative paths with a form that resolves in the target — the installed skill name, or an absolute repo URL.
    • Remove the six invented tool names; name the servers, not their tools, and let each SKILL.md own the tool list.
    • Delete the "Architecture and Implementation Rules" block — it is sibling-analysis-repo's domain, not a starter's.
    • Ship what the starter currently only describes: a .mcp.json template, a tracked .claude/settings.json, and .gitattributes (the CRLF-shebang trap is a hard rule here and every new repo needs it on day one).

    Then test it the only way that catches this class of bug: copy the starter to a throwaway directory outside agent-skills and resolve every path and every tool name from there.

  3. Track .claude/settings.json; leave the token behind

    ~15 mintrackedfresh clone works
    {
  "enabledMcpjsonServers": ["omnigraph"]
}
// .claude/settings.local.json keeps env.OMNIGRAPH_TOKEN — and nothing else

    Verify by cloning into a throwaway worktree and confirming Omnigraph comes up without settings.local.json, the token aside. Pair it with a permissions.allow pass; /fewer-permission-prompts mines this machine's transcripts to generate one.

  4. Add tests/ at the root — four invariants

    ~2 hrtrackedmakes 1–3 durable
    • Skills resolve. Every directory under skills/ has valid frontmatter whose name matches the directory, and appears in whatever manifest the load path uses.
    • The router is complete. Every skill has a row in repository-index/SKILL.md §3–§5. True today; CONTRIBUTING.md requires it and nothing keeps it true.
    • No personal paths. Fails on the nine files above until they are fixed — a test that starts red and can be watched turning green.
    • Starters resolve from outside. Copy to a temp dir; assert every referenced path exists and every named tool is real.

    Hooks are the heavier half of the same idea and belong with ADR 0004's generated adapter. These four are plain pytest and need nothing from it.

  5. Clear the strays and the rules that hide them

    ~20 min671 MBfaster lookups

    Delete mcp-servers/, antigravity-remote-ui/ and agent-skills/ from the repo root — check each .env for anything worth keeping first. Then drop the 15 .gitignore rules that describe the retired layout, and set ignored_paths in .serena/project.yml to cover graphify-out/ and .claude/scratch/.

    One documentation fix belongs here too: structured-memory/references/{schema,operations}.md show insert <Edge> { from, to } but no node insert example. Writing insert Component { data: { … } } from the edge pattern fails with parse error: expected match_value; the correct form is flat (insert Component { slug: $s, name: $n }). Measured this session — one wasted round trip, and it will repeat for every agent that writes to the graph.

Boundaries

What not to change

  • Keep Omnigraph as the only memory layer. ADR 0003 settled it and the graph holds 22 Rules and 17 Decisions. Nothing here proposes a second store — the tests carry procedure, the graph carries why.
  • Keep docs/decisions/. This repo's ADRs are a deliberate choice and unlike sibling-analysis-repo it does not route the ADR half of P5 to the graph. Do not import that repo's boundary along with its findings.
  • Leave AGENTS.md long enough to be useful. At 107 lines it is well inside the guidance the downstream audit cites. The .claude/rules/ path-scoping work it recommends is the right answer there and would be premature here.
  • Do not give graphify a per-repo entry. One cwd-relative user-scope entry serves every repo; the starter must keep saying so, since a per-repo entry is a documented failure with a checker already written for it.
  • Do not hand-write the .claude/ orchestration adapter. ADR 0004 says generated, and the reason — model tiers drifting between the YAML and the adapter — still holds. Steps 1–5 above touch no part of that surface.
Proving it landed

Verification, in this repository's own terms

Each check can come back negative. That is the point — CONTRIBUTING.md asks for checks that fail loudly, and a mechanism nobody has watched fail has not been verified.

  • Skills: the names appear in the session's skill listing after a restart on a machine that has never had the symlinks. Not "the files are there".
  • Starter: copied to a temp directory outside this repo, every path resolves and every named tool exists. The test does the copying.
  • settings.json: a throwaway clone brings up Omnigraph with only the token supplied out of band.
  • Tests: the personal-paths test starts red against today's tree. A test that has only ever passed proves nothing about what it would catch.
  • Strays: git status clean, du -sh on the repo root down by ~658 MB, and a Serena symbol lookup that no longer walks them.

Two of these have already been run: the MCP mandate is in the four files above, and the graph now carries the Decision and both Rules — as-dec-mcp-stack-mandatory-in-instructions, as-rule-a-skill-needs-a-load-path, as-rule-starter-pointers-must-resolve-downstream — each edged to the agent-skills Project and to the components it governs, and read back after the write.
